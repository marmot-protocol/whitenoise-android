# Controlled attachment latency matrix, baseline, 2026-10-03

Context: [#2785](https://github.com/marmot-protocol/whitenoise-android/issues/2785). This is the controlled baseline for
attachment latency: where upload and download time and memory go, per layer, on declared links, measured through the
shipping send controller and resolver. It changes no shipping behavior. It is an **emulator and loopback** measurement
with a server-shaped link. It does not qualify physical Wi-Fi, a production network or the target budgets, and the
strict 1 KiB budgets elsewhere are unchanged.

## Method

A generated sender and receiver share a private group. For every sample the probe, in the shipping app process:

1. **Uploads** a generated file through `ConversationController`, split into the synchronous preparation the reader
   sees and the upload-and-publish half.
2. **Cold downloads** it on the receiver with the production observer, beside an authoritative 2 ms read-only poll of
   the engine and a recorder of the engine's own feed, so each phase has a time.
3. **Warm reads** the retained file.

After a link's samples the host force-stops only the isolated package and a new process reads one kept file per size
from retention with acquisition unavailable ("restart").

The **server** is the authority. A loopback Blossom server shapes bandwidth and latency in both directions, commits an
ordered ledger event per request, byte batch and completion, and brackets every sample with a numbered marker, so each
sample owns exactly its own requests and bytes. `matrix_report.check_matrix` fails closed on a missing sample or marker,
any retry, HEAD or refetch, an inexact ciphertext byte count, a missing restart read, an acquisition after the restart
boundary, or a shaped label the server did not observe (a link is rejected if the body arrived faster than declared).
Every sample carries only a size, a repetition and measurements: no file name, identifier, URL, key or content.

| Link | Shape (down / up, latency) | Sizes and repetitions per run |
| --- | --- | --- |
| unshaped | loopback | 64 KiB x20, 1 MiB x10, 8 MiB x5, 30 MiB x3 |
| wifi | 50 / 20 Mbit/s, 20 ms | 64 KiB x10, 1 MiB x5, 8 MiB x3, 30 MiB x1 |
| constrained | 4 / 1 Mbit/s, 120 ms | 64 KiB x5, 1 MiB x3, 8 MiB x1 |

Three runs are pooled at the sample level, so the spread includes run-to-run variation. A p95 is reported only for a
cell with twenty or more samples (in the aggregate JSON), never inferred from fewer.

Reading the tables:

- **Engine feed delay** is the gap between the engine reporting `READY` and its subscription delivering that frame,
  seen by the probe's own recorder. **Post-READY wait** is what the shipping path adds after the authoritative `READY`
  until the file can be opened: delivery plus materialization. Their difference is what the host pays for the engine's
  delivery cadence.
- **Open-ready lease** is the whole cold download as the reader experiences it. **Restart native lease** reads retained
  bytes after a process restart with no network.

## Where the time goes

1. **Small files wait on the engine, not the network.** A 64 KiB cold download is ready in the engine after 34 ms but
   opens after 265 ms: 223 ms (84% of the download time) is the engine coalescing subscription frames to one per 250 ms,
   including the terminal one. The wait is up to 250 ms on every download, so it dominates wherever the transfer itself
   takes a few hundred milliseconds or less: 64 KiB on every link and 1 MiB on the unshaped link. It is an engine
   delivery property that the host can bypass without changing the engine.
2. **Transport dominates from 8 MiB on shaped links and in every upload on shaped links.** At 4 / 1 Mbit/s an 8 MiB
   download is 19.1 s and the upload 70.5 s, with the server upload more than 99% of the upload. The server paces in
   chunks, so the 50 Mbit/s link delivered about 29 to 31 Mbit/s and the 4 Mbit/s link about 3.4 to 3.5 Mbit/s. The
   checker proves a link is not faster than declared, not that it is saturated.
3. **Engine upload cost is about 25 ms/MiB for large files** on the unshaped link (738 ms for 30 MiB, 222 ms for 8 MiB),
   the encrypt and request work around the server's own time.
4. **Materialization is a whole-file copy.** Making retained bytes openable takes 9 ms up to 1 MiB, 58 ms for 8 MiB and
   542 ms for 30 MiB, and the same 520 to 560 ms again on every warm read and after every restart at 30 MiB. That is the
   Android storage layer copying native plaintext into an owner-private lease.
5. **Memory follows the whole-array boundary.** At 30 MiB the sampled Java peak is 66 MiB when sending and 89 MiB when
   receiving, with native peaks of 229 and 169 MiB. Small files stay near 13 to 20 MiB Java and 73 to 79 MiB native.
6. **Preparation is not a cost.** The synchronous preparation the reader sees is 0.9 to 1.8 ms at every size.
7. **Correctness held in every pooled sample.** Each recorded exactly one upload and one GET, no HEAD, no retry, exact
   ciphertext bytes up and down, and the restart reads never acquired.

## What failed, and what it found

- **Run 2** failed on an unshaped 30 MiB upload: the reference did not appear within the probe's 30 s wait. Its logcat
  was not kept, so the cause is inferred from the next item.
- **The constrained 30 MiB cell cannot be measured.** The server received every byte after 267 s and the engine then
  rejected the finished upload: `media reference was encrypted at epoch 2 but the group is at epoch 3; upload it again`.
  The pinned engine rotates a joined account's leaf after a quiet period plus up to 30 s of jitter, the likely source of
  the epoch change that fell inside the long upload. The cell is omitted from the plan. The behavior is real beyond this
  fixture: an upload that spans a group commit is rejected after all its bytes were sent, and a slow link makes that
  window minutes long. It belongs to the engine and is raised with MDK.
- An earlier three-run set (without the constrained 30 MiB cell) passed and agrees with these numbers.

## Limits

An emulator on an Apple Silicon host, loopback, with server-side shaping: no radio, no DNS, no TLS, no physical Wi-Fi
and no production relay. The numbers locate delays by layer and compare heads; they are not field latency. Memory is the
maximum of samples taken every 50 ms plus the stage endpoints, so a shorter spike can be missed. Near-limit sizes have
three and one samples per run, so they are correctness and memory observations, not stable p95 estimates. The
constrained near-limit cell is absent for the reason above.

## Reproduce

```bash
bash scripts/run-controlled-attachment-fixture.sh emulator-5554 Play reference-api30-arm64 controller-matrix unshaped,wifi,constrained
python3 tools/attachment-fixture/matrix_tables.py --baseline run-1.json run-3.json run-4.json
```

Raw reports, logs, APK digests and verified checksums for the passing, failed and diagnostic runs stay private and
durable. Compare a candidate with `matrix_compare.py --baseline ... --candidate ...`: a change counts only when it
exceeds the observed spread and ten percent, any difference in requests, bytes or retries rejects the candidate, a
profile or size measured on only one side rejects it as incomplete, and only reader-visible metrics can reject it for
being slower. Every baseline and candidate run is first held to the same correctness check that gated its own report,
and the command exits with status 2 without comparing anything when one fails: an extra HEAD inside a sample leaves
every aggregate unchanged, so it can only be seen there. The preserved baseline run that failed its checks (run 2 of
the first pairing attempt) is rejected by this check, which is why the comparison uses runs 1, 3 and 4.
