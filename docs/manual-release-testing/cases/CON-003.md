1. [ ] **CON-003 — Pagination** — Scroll repeatedly to the oldest prepared messages, briskly enough to cross several pages without pausing, in a conversation holding more than 200 messages. On a debuggable build, Settings → Developer Tools → Seed conversation fixture prepares such a conversation from a private test group. Then repeat while the engine is busy, for example on the first launch after a long time offline, and with **Settings → Developer → Diagnostics → Performance logs** enabled. Create a reply whose visible quote contains an original outside the current retained window, then tap that quote while the engine is busy and again after it settles. → **Expected:** Older pages load early enough that a fast fling crosses ordinary page boundaries without stopping and restarting; pages contain no duplicates, jumps, or lost content; end-of-history is stable; the bottom-anchored transcript extends its far end without moving the row being read; older and newer pages extend the window without losing the row you were reading. Scrolling back towards newer messages fetches the next page with the same half-page of runway as older history, so a fling down never rests on the newest loaded row waiting; newer-page fetching never overlays a message bubble or shifts the list's bottom edge; explicit failed navigation still offers its retry row; automatic edge prefetch recovers quietly. Rows you have already paged past stay in the transcript, up to a few hundred, so paging back towards them, a message arriving while you read history, and returning to the newest edge reuse what is loaded instead of rebuilding the list; only a window that cannot be lined up with the loaded rows rebuilds it — a jump to a place in history sharing no loaded row, or a page whose shared rows no longer sit at one consistent offset because a message was inserted or removed inside their span — and such a rebuild is expected, not a regression. A hydrated reply target outside the loaded rows recenters and highlights its exact original; a delayed or superseded window command retries briefly; if revision churn continues, the notice tells the reader to retry and tapping the same reply quote again repeats the jump, while only an explicit native missing-target result shows the unavailable message. During repeated sends or relay echoes, verify that an upward page can advance after a superseded response and that a persistent automatic race stops quietly without a red retry row or endless spinner, and a new drag can re-arm it. Keep the viewport still while a native recovery arrives before the pending failure reply: paging must automatically resume without another drag. A short successful page that leaves the same visible anchor within the prefetch margin continues loading older rows. Deliver the native command response and stream echo in both orders: one successful page must never be mistaken for failure or move history twice, including when a newer content-only replacement overtakes its reply. A newer viewport remains authoritative instead of reinstalling the old command result. After enough older paging to evict the last-read message from the bounded window, the jump badge still shows the authoritative unread count rather than counting the loaded history, and its number does not move while pages load or rows leave the loaded window — it is right from the first frame after opening, with nothing unread it stays absent through every page, and it changes only when a message arrives or you read past unread rows, never flashing 0 or a page-sized count in between; tapping it goes first to the oldest unread message while unread remain, and the next tap — or the first, with nothing unread — returns to the physical newest edge in one action, landing there in one snap when the newest row is more than 10 list items away, and animating into it when it is at most 10 items away. The row under your finger stays put across every page, and rows already on screen do not visibly re-render or re-lay-out after a page arrives. When automatic older prefetch reaches a deadline or receives not-ready, keep the loaded transcript visible without a red error or Retry message. It waits for a successful native replacement, including one that arrived before the error reply, then resumes from the visible anchor. Repeated layout passes and drags while not-ready must not poll or reopen the window. A queued echo of the failed attempt cannot restart it. A late older page clears its obsolete explicit older retry without dismissing newer-navigation or subscription errors. Switch chats/accounts during a delayed page: no late rows may reach the replacement conversation. At the start of history, an engine that still claims older messages but delivers none is asked once: the header then rests on its refresh row with no spinner, nothing is requested again until a new drag, a deliberate header refresh, or a newer live window arrives, and the app sits idle instead of paging in a loop. A second flick made while the transcript is still coasting carries on from where the finger caught it, with no snap back to the first release point, and a page landing mid-fling never snaps the list back to where the finger lifted. Window preparation does not stall scrolling or composer input, and if two updates overlap only the newest prepared generation commits. With performance logs on, `WNPerf` lines for `op=chat_history_page` report `page_window` and `page_apply` for each page, and `page_apply` stays well below `page_window`.
