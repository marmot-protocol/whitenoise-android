[ ] **MED-027 — Oversized received image previews** — On disposable accounts, receive from another client a valid image whose plaintext is just under 32 MiB and one just over it (a PNG or JPEG of noise reaches these sizes), each once as a single image, once inside an album and once as an inline custom emoji. With image automatic downloads on, scroll each into view and open it in the full-screen viewer, then use More → Save and Share on the oversized one. Repeat with every image automatic-download cell off while MDK still retains the bytes, repeat after the Android presentation cache has been evicted, and repeat after tapping the oversized tile while its download is still running. Watch memory with the device's developer options or a heap dump while the oversized image is on screen. On a debuggable build, also list the app's `cache/native_attachment_leases` directory with `adb shell run-as` while the oversized image is on screen in the automatic-downloads-off pass. → **Expected:** The image under the ceiling renders in the bubble, the album tile, the emoji slot and the viewer as before. The oversized image's bubble and album tile show Too large to preview over the thumbhash, with no spinner and no Retry, and a tap opens the viewer rather than starting a download; the viewer shows Too large to preview with the Save or share hint and no Retry, while More → Save writes the exact image to the gallery and Share hands the exact bytes to the chooser. The oversized emoji leaves its shortcode as text. No new transfer starts from any of these states, the app never allocates the whole oversized image on the heap for a preview and never runs out of memory, and a tap made while the download was running lets it finish in place without opening anything; the next tap opens the viewer. In the automatic-downloads-off pass that lease directory stays empty, because refusing the oversized preview never writes a temporary copy of the image first. Rotation, recreation, background and return keep the same state.
