[ ] **MED-034 — Received media downloads in the background** — With a disposable receiving account, set Settings → Data Usage so images, videos, audio and files download automatically on Wi-Fi, connect to Wi-Fi and press Home so White Noise's Activity is stopped. From a second device, send into a chat the receiver never opens: an image, an animated GIF, a short video, a voice note, an audio file and a small document, as one album and as separate messages. Wait two minutes without opening the app, then open the chat with the network turned off. Repeat in a muted chat, for a receiving account that is not the active one, and with White Noise's process killed by the system (for example with `adb shell am kill` while it is in the background) while a large file downloads. Then turn Wi-Fi off with videos still enabled for Wi-Fi only, send a video, wait two minutes, and turn Wi-Fi back on without opening the app. Turn videos off on every network, tap Stop automatic downloads, sign the account out, and fill the device until Android reports low storage, each time sending a fresh album. Also send media on Wi-Fi with videos enabled, then turn videos off before or while Android runs the queued download. Separately, deny White Noise's notification permission and send an album, and with push and the background connection both off, send an album and open the app only afterwards. Afterwards read the `DMAttachmentReceipt` and `DMAttachmentWorker` lines in logcat. → **Expected:** With the network off, every enabled type in the unopened chat renders and plays from local data, including in the muted chat, for the inactive account and after the system killed the process, and opening the chat starts no new network transfer. The video sent without Wi-Fi is not fetched until Wi-Fi returns, then downloads without opening the app. A type turned off everywhere, a stopped backlog, a signed-out account and low storage leave those attachments remote with a manual Download control, and a type turned off before or during its queued download is not fetched to completion; a download already running frees its slot within about a minute. With notifications denied, media still downloads in the background and no notification appears. With no background delivery, nothing arrives until the app runs, then the media is scheduled as the messages arrive. Media received while White Noise was force-stopped is not downloaded until the app runs again; that is outside this check. Each receipt with attachments logs one `attachment_receipt_scheduled` line with queued, waiting and held counts, held types, pages read and how the read ended; a receipt for a stopped backlog or signed-out account logs `attachment_receipt_skipped` with its reason; a queued download that policy holds back logs `attachment_work_policy_deferred` with its type, reason and whether it waits for a network. None of these lines names an account, chat, message, file name or attachment index. Received media never raises a sound, vibration or extra notification beyond the message's own notification.
