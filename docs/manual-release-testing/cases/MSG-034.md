1. [ ] **MSG-034 — Send your custom emoji in a message** — Add `:party:` and `:ship_it:` in Settings → Appearance → Custom emoji. In a group and a direct chat with a 0.12.0 peer, send `hi :party: and :ship_it:`, then `:party:` alone, then `see :unknown_code:`, then `` `:party:` `` in a code span, then a reply that uses `:party:`. Send `:party:` twice in a row and note the network activity. After the chat advances at least one epoch (add or remove a member), send `:party:` again. Switch off the network before one send and reconnect, then repeat with a send that fails after the image uploaded. Remove `:party:` in Settings and send it once more. With a legacy `old.img` emoji present (see SET-030), send `:old:` once and send `:old: :party:`. Open Shared media and the photo viewer in both chats. Send `:party: :parrot:` where both emoji use the same image. On a disposable fixture, include duplicate artwork locators with aliases, a real photo in the same album, and a malformed five-field emoji tag. Compare the message attachments, recent-media strip and full history library. On a slow connection, cancel a send while its image is uploading, then cancel another right as it publishes. → **Expected:** The peer sees your image inline in place of each defined shortcode and no extra photo attachment. An unknown code, a code span, a reply, a code you removed and a legacy `.img` emoji are sent and shown as literal text, and the legacy emoji's image is never uploaded, so the peer sees only `:old:`, while `:party:` in the same message still sends its image. The Shared media gallery and the photo viewer never list emoji images, while a real photo in the same chat still appears. The image is uploaded once per epoch and reused by the next send and by any retry. A connection loss before the upload completes keeps the bubble Pending and retries automatically when the connection returns without a duplicate. A failure after upload shows Failed with Retry. If the chat changed while sending, the failure says so and Retry succeeds. Two emoji sharing one image both render on the peer. Every valid duplicate artwork slot is excluded on all three surfaces, but each shortcode still materializes only its first matching image and aliases share that read; an unavailable first image does not trigger a duplicate-slot download. A malformed five-field tag leaves the image shared and cannot shadow a later valid definition. Shared photos retain their original slot indexes. Cancelling during the upload sends nothing and removes the bubble, while cancelling right after the publish shows "Couldn't delete message" and the bubble stays, because the message is already published. A message over MDK's limits fails before anything is uploaded, with a specific message about too many custom emoji. The message still opens, replies, reacts and copies as its literal text on both devices, including after the epoch change. The chat-list preview of a message that carries emoji images may read as a photo, which is MDK's preview and not a defect of this change.
