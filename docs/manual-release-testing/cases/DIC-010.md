[ ] **DIC-010 — Slow caller-audio Send and bounded recovery** — With a caller-audio speech provider and a disposable chat containing a known draft, dictate several phrases including a distinctive final phrase. Press Send while a long captured chunk is still processing, then open another chat whose draft contains different text. Exercise a delayed provider result arriving more than 20 seconds after Send but within the 90-second total drain budget. Repeat when the provider has already reported End of speech before Send, and with several queued chunks and replacement recognizers. Separately exercise a provider that stays unresponsive for the whole drain budget, then Retry; repeat with exhausted recognition failures. → **Expected:** The accepted Send waits for every chunk within one original 90-second drain deadline and sends the complete text exactly once to the original chat. The other chat's draft is unchanged. The 20-second generation-processing watchdog does not preempt caller-audio draining; ordinary provider-owned processing remains bounded. A drain timeout or exhausted recognition failure preserves the recognized prefix and unresolved audio for recovery, awaiting an explicit recovery action. Retry starts a fresh bounded attempt; stale callbacks from the failed attempt cannot insert or send anything. Cancellation releases resources and prevents late completion. **Pending send lifetime.** Delay message transport for more than 20 seconds after the outgoing pending bubble appears, leave the chat and return, then restore connectivity. Start another recording while the first send waits. → **Expected:** Each requested message sends once through the ordinary sender; the first send remains pending across the dictation deadline and completing the newer recording cannot cancel it. A definite terminal failure uses the ordinary failed-message recovery without silently reporting delivery. **Completion edge cases.** Finish Send after leaving the origin chat while native sending is retained pending convergence; return after reconnecting. During a separate capture, open an existing message for editing before Send completes. Exercise a composer that definitively refuses a send before a pending bubble appears, then restore its availability and retry. → **Expected:** A detached native retained result with its event ID still pending keeps its transcript recoverable with delivery unknown; Retry leaves the attempt count unchanged. Confirmed publication may complete before its event echo arrives. A new edit session stays intact and receives no dictated edit. A definite pre-send refusal retains the transcript with a retryable blocked-send result; an already pending failure stays under the ordinary sender’s ownership.
