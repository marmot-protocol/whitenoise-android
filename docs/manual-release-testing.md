# White Noise Android manual release testing

This is the release-candidate checklist for every user-visible White Noise Android surface. It is written so a tester who has never used White Noise can follow it without reading the source. Run every applicable point against the exact APK proposed for release. Do not infer a pass from an automated test.

## How to use this guide

1. Record the APK filename, SHA-256, version, build variant, commit SHA, Android version, device model, tester, and date in the run report.
2. Work from a clean install unless a point explicitly requires retained data or an upgrade. Keep one separate populated installation for upgrade and history checks.
3. Tick a point only after performing its **Actions** and observing its **Expected** result. Record `N/A` only when the point's stated prerequisite is unavailable, and write why.
4. Report failures by the stable point ID, for example `MSG-006`, plus account, conversation type, exact actions, actual result, screenshot or screen recording when safe, and relevant time. IDs are permanent: they are never renumbered or reused.
5. When a point says “the other device,” use another real installation signed in to a different test identity. Allow normal relay latency before failing a synchronization point.
6. “Back” means test both the visible back arrow and Android system Back where both are available. A screen passes only if neither path exits unexpectedly, loses a draft, or returns to the wrong account.

## Safety and test-data rules

- Use disposable test identities, test relay data, synthetic names, synthetic phone contacts, harmless files, and a non-sensitive test location. Never paste a real `nsec`, recovery phrase, contact book, private photo, audit log, or precise home/work location into a report.
- Treat account keys, encrypted backups, QR codes, notification content, exported audit logs, and the Android share sheet as sensitive. Blur or omit their values from evidence.
- Use a dedicated temporary directory for downloads and exports. Delete it, clear the clipboard, remove test accounts, and revoke temporary permissions after the run.
- Before destructive points (wipe, leave, remove member, delete for everyone, disappearing messages), confirm that every affected identity and conversation is disposable.
- Test notification text on a locked device only with synthetic messages. Do not expose private content on a shared lock screen.
- Never approve an unexpected Android permission prompt. A requested permission must correspond to the action described in the current point.
- Use only tester-controlled identities and test relays. Never invite, message, or add an account that the tester does not control. Relay-published profile, membership, and message data can be copied permanently even after local deletion, so use only synthetic, non-sensitive content. Prefer a dedicated test/staging relay set; if none is available, clearly mark the run as using public relays and keep all content disposable.

## Test matrix and prerequisites

- One supported Android phone with a secure device credential; a second Android device or emulator; and, when available, one Android 13+ device for notification permission behavior.
- Three disposable identities: Alice (primary tester), Bob (peer), and Carol (group member). Keep Alice signed in on the release candidate and Bob/Carol on independent installations.
- One direct chat with Bob; one three-person group with Alice as admin; one group where Alice is a non-admin; an invite awaiting Alice; populated and empty/archived chats; and messages from each member.
- Safe fixtures: short and long text, emoji, a web URL, `@`-mentionable members, small/large images, video, audio, PDF, plain-text document, unsupported file, synthetic vCard contact, and a coarse test location.
- Test both the Zapstore and Play build behavior when producing those artifacts. Build-specific points may be `N/A` for a release that does not ship that variant.
- For accessibility coverage, enable TalkBack, large display/font settings, an RTL locale, landscape, dark theme, and reduced-animation settings one at a time.

## Smoke pass

Before the exhaustive pass, run these release-blocking paths in order: `INT-001`, `ONB-003`, `CHL-002`, `CON-005`, `MED-003`, `MSG-005`, `GRP-012`, `NTF-009`, `SEC-002`, `SET-025`, and `END-004`. A smoke failure stops the release but does not replace the full checklist after repair.

### Release identity and first launch

1. [ ] **INT-001 — APK identity** — Install the recorded APK and open Android App info. → **Expected:** The app name, icon, package, version, and build variant match the release candidate; a development or staging build is visibly distinguishable from production.
2. [ ] **INT-002 — Clean launch** — Clear app storage, force-stop, then launch from the launcher. → **Expected:** The system splash hands off to White Noise once, startup never shows another account's content, and onboarding appears without a crash or blank frame.
3. [ ] **INT-003 — Startup progress** — Launch on a slow connection in light and dark themes. → **Expected:** The native splash mark remains legible against its background and promptly hands off to a meaningful, responsive secure-startup/loading state that resolves to onboarding or the signed-in surface. With a previously saved profile, force-stop/relaunch and install a compatible update in place while offline: the first Chats frame uses the active account’s saved name and avatar reference. Record avatar metadata readiness separately from whether image pixels were already cached; a true local profile miss may show initials. Repeat after editing/removing the picture and during rapid account switches; an old account’s profile must never appear. If runtime recovery interrupts activation, check that the recovered account's profile and notification preferences remain correct; deferred refresh steps from the replaced runtime must not start afterward.
4. [ ] **INT-004 — Startup retry** — Disable networking during startup, wait for the timeout/error, restore networking, and tap Retry. → **Expected:** The error explains recovery, retained content is not discarded, and retry reaches the usable app without relaunching.
5. [ ] **INT-005 — Warm resume** — Open a conversation, background the app for 30 seconds, and resume it from Recents. → **Expected:** The same account and useful surface return without a second splash, duplicate navigation, or stale overlay.
6. [ ] **INT-006 — Process recreation** — With a conversation open, use the developer option “Don't keep activities” or kill the process, then reopen. → **Expected:** The app restores or safely falls back to the correct account and chats; the first restored chat-list frame uses the selected titles and avatars, never flashes “Unknown,” and never shows another account's messages.
7. [ ] **INT-007 — Offline shell** — With populated local data, disable all networks and relaunch. → **Expected:** Existing chats/messages remain readable, an offline/retrying state is honest, and network-only actions fail safely without deleting local content.
8. [ ] **INT-008 — Connectivity recovery** — While the offline shell is visible, restore networking and receive/send a synthetic message. → **Expected:** Connection indicators recover without an app restart and the new message appears once.
9. [ ] **INT-009 — Recents privacy** — Open a conversation, enter Android Recents, and inspect the task preview. → **Expected:** The preview is protected according to Device privacy settings and does not expose chat content when screenshots are blocked.
10. [ ] **INT-010 — Upgrade with retained data** — Take a private backup and record the installed version, then install the candidate in place over the previous release containing prepared private-key and Amber accounts/chats, without uninstalling or clearing storage. Open each account, check its relay settings, send and receive a synthetic message, then force-stop and reopen twice. For a MarmotKit SDK update, also run `ONB-006`, `ONB-008`, `ONB-012`, `ONB-017`, `ONB-018`, `ONB-020`, `SEC-007`, and `SET-019` to cover fresh sign-in, recovery, signer integration, and build identity. → **Expected:** Both account types reach usable chats without a startup or migration error; relay settings, drafts, folders, and message history remain available; messages appear once; and migrations do not repeat or reset user choices on subsequent launches. MarmotKit 0.9.20 advances account migrations 65–67 and shared storage 2–3; keep the pre-upgrade backup because downgrade is unsupported. Previous telemetry consent requires a fresh choice as covered by `SEC-007`.

11. [ ] **INT-011 — Avatar recovery** — With retained profile and group metadata, turn off Wi-Fi and mobile data, force-stop the app without clearing its data, and reopen. Keep the missing profile/group avatars visible, then restore networking. Repeat while the app is backgrounded, return to it, and switch accounts while an avatar is loading. → **Expected:** Missing visible avatars retry when validated internet returns, without restarting the app, navigating away, or waiting for the previous failure cooldown. A backgrounded screen waits until visible before retrying. Already-loaded pictures do not flash back to initials; a late old-account image never replaces the selected identity. A genuine remote image failure keeps the fallback without a polling loop. This check does not promise offline image persistence after process death.

7. [ ] **ONB-007 — Sign-in failure and retry** — Interrupt the network after submitting a valid disposable key, wait for failure, restore it, and retry. → **Expected:** The error distinguishes retry from invalid input and retry succeeds without duplicate accounts.
8. [ ] **ONB-008 — Setup recovery consent** — Sign in with a fixture whose remote setup requires recovery, read the warning, cancel once, then confirm. → **Expected:** Cancel leaves setup unchanged; confirm runs one recovery attempt and reports success or a specific failure without repeatedly prompting.
9. [ ] **ONB-009 — Saved-account continuation** — Sign out without wiping a retained test account, return to onboarding, and tap its saved-account action. → **Expected:** The named account shows a single reactivation progress state and returns to that account.
10. [ ] **ONB-010 — Amber absent** — Use a device without a NIP-55 signer and open onboarding. → **Expected:** Login with Amber is not offered and ordinary key sign-in remains available.
11. [ ] **ONB-011 — Amber present and cancelled** — Install Amber, tap Login with Amber, then cancel in Amber. → **Expected:** White Noise returns to onboarding, clears its busy state, and creates no account.
12. [ ] **ONB-012 — Amber success/error** — Complete disposable Amber login, then repeat with a denied or failed signer response. → **Expected:** Success opens setup for the matching account before Chats; denial/failure shows a recoverable result without exposing key material or trapping the UI.


13. [ ] **ONB-013 — Automatic imported-account setup** — Import a disposable nsec with healthy published metadata, then repeat with a fresh identity missing profile, follows, and relay lists. Repeat with Amber. → **Expected:** Healthy profiles pass automatically. A missing name/profile offers Edit profile and Not now; neither choice is submitted automatically. Follow-list and missing-relay confirmations are omitted: native checks skip optional follows without publishing a replacement and add safe relay defaults automatically. The six-row checklist, account key, and secondary controls are hidden until Details is opened; Hide details collapses them. Test portrait, landscape, tablet, large fonts, and RTL. If Not now is selected, the name can be added later through the existing profile UI.
14. [ ] **ONB-014 — Optional name setup and Amber approval** — Import a fresh disposable identity. Choose Edit profile, enter a name, review it, and approve publication. In a separate run choose Not now and verify setup continues. Also resume an unapproved saved profile proposal, discard once, then approve a new edited draft. Repeat with a disposable Amber account and deny its profile-signing prompt once before retrying. → **Expected:** A restored user-authored proposal never becomes an automatic default. Other profile fields remain unchanged; failed drafts remain editable; denial leaves a recoverable screen without a prompt loop. Fresh imports with missing profile details offer editing or skipping; healthy existing profiles pass automatically.
15. [ ] **ONB-015 — Discovery failure and retry** — With an unreadable or unreachable relay fixture, inspect the finding, retry, and enter another discovery relay. → **Expected:** Findings distinguish invalid, unsafe, retired, restricted, unreachable, and timed-out endpoints. The current finding names its affected relay address directly on the decision screen, without opening Details; findings with no endpoint show only their explanation. Discovery-only changes publish nothing. An inconclusive lookup offers retry/discovery rather than silently publishing defaults.
16. [ ] **ONB-016 — Destructive relay replacement review** — Import a fixture with a broken relay entry that requires cleanup. Choose recommended or custom relays, inspect the full proposed list, discard once, then approve. → **Expected:** Removing or replacing existing entries requires explicit consent. The concise warning explains that omitted relays are removed and other Nostr apps are affected. Read/write capabilities and exact inbox endpoints match the reviewed proposal. Inbox and discovery editors retain distinct labels. A proposal from another step never appears under the current decision. Discard does not automatically recreate or publish the proposal.
17. [ ] **ONB-017 — Stale proposal and interrupted publication** — Leave a proposal visible while another controlled test installation changes that relay record; attempt approval. Separately interrupt an already approved publication and resume. With a controlled recovered-checkpoint fixture, change the recovery attempt while keeping its proposal revision unchanged, then try the previously displayed approval and review the refreshed proposal. → **Expected:** A changed decision or recovery attempt requires fresh review; a prior approval cannot authorize the replacement attempt, even when its revision is identical. An unapproved restored proposal stays unapproved; an approved interrupted publication retries its saved operation without requesting a replacement proposal or claiming the earlier publication can be undone.
18. [ ] **ONB-018 — One-device acknowledgment** — Reach the device notice with fixtures for no discovered packages, another possible installation, and incomplete discovery. Read the short notice and tap Use this device. Repeat using a controlled recovered-checkpoint fixture; replace its recovery attempt at the same revision before tapping, then review the refreshed notice. → **Expected:** The app explains that chats stay on this device and do not sync. Details explains each discovery outcome, including no usable packages and an inconclusive check. A possible other installation gets an additional concise warning; the app never claims another device is online or absent. Initial messaging keys publish only after acknowledgment of the current attempt; stale device consent must be rejected. The normal notice shows Use this device and Details, without Retry or Finish later. Back still saves and exits. A genuine failed check shows its reason and retains Retry and Finish later. No second key approval or final Open Chats tap is required. If Opening your chats… appears during activation, it resolves to Chats without another tap.
19. [ ] **ONB-019 — Later and restart** — During checks and while a decision is pending, use Finish later or system Back, select the saved account to resume, rotate, then force-stop and relaunch. Repeat after returning from Amber. → **Expected:** MDK's saved progress resumes without repeating completed repairs, losing an unapproved proposal, switching to the wrong account, or trapping the screen in a spinner. Pending setup does not open Chats or ordinary push/maintenance work. Completing resumed setup restores notification-receiver readiness and privacy settings before Chats opens.
20. [ ] **ONB-020 — Add account and cancel** — From a populated account use Add account to import another disposable nsec or Amber identity. Leave setup for later, resume, open Details, and cancel at the device notice. → **Expected:** Defaults run without activating the pending account; leaving returns to the original usable account. Cancel retains the new identity signed out and completed publications. Repeat cancellation during an approved or interrupted publication and while Amber holds a signing request, then complete the late response and restart the app. The cancelled attempt stays signed out and cannot be revived by that response. A later explicit sign-in starts a fresh attempt while MDK retains evidence of uncertain publications; cancellation never claims to undo a publication.
21. [ ] **ONB-021 — Direct completion and recovery** — Tap a genuine decision twice quickly; reconnect Amber after denial/unavailability. Deny an automatic relay-default signature once, then retry explicitly. Interrupt final activation and retry when available. → **Expected:** Only one operation starts per tap sequence. Signer rejection restores retry controls without another automatic prompt. Once ready, fresh native verification enters Chats automatically, with no Later/help/checklist chrome at completion. An activation failure retains a working explicit retry.
22. [ ] **ONB-022 — Offline identity acceptance** — Disable networking, submit a new disposable nsec, and then restore the connection and resume checks. Separately try Sign up while offline. → **Expected:** nsec acceptance clears the key and opens saved/retryable preflight without requiring network validation. Sign up retains its existing offline notice and retry behavior.
23. [ ] **ONB-023 — Defaults preserve existing relay lists** — Import disposable accounts with healthy existing lists, a confirmed-missing list, and a read-only list with no write route. Repeat with incomplete discovery. → **Expected:** Healthy lists pass unchanged; confirmed-missing lists receive defaults without a confirmation tap. Existing lists that need repair stop for review before any replacement is published. Incomplete discovery never authorizes automatic defaults or removal. If a record appears between discovery and approval, setup stops for fresh review.
24. [ ] **ONB-024 — Unreadable saved-checkpoint recovery** — Open onboarding with a disposable saved profile whose setup checkpoint is unreadable or exhausted. Also simulate a transient failure while reading its recovery state at launch and from the account picker, then retry after the read succeeds. Tap its Recover sign-in setup action, cancel once, then confirm and enter that profile’s private key again. → **Expected:** A failed recovery-state read fails closed: the account stays out of Chats and ordinary background work instead of being treated as ready, and a later successful read routes to the correct saved setup or recovery surface. An unreadable checkpoint is not treated as ordinary resumable setup. Confirmation explains sign-out, latest-only recovery evidence, and that prior publications are not undone or approved. Cancel changes nothing; confirm acknowledges the latest evidence once, retires the unreadable attempt, and requires a fresh sign-in without exposing or retaining the private key.

- `README.md`, `docs/`, `.github/workflows/android-ci.yml`, and release/verification scripts

A feature is in scope when a release build can present it to a user, including loading, empty, disabled, permission-denied, offline, error, retry, destructive-confirmation, account-switch, background, and restored states. A visible Coming soon control is tested as a disabled/explicit state; a source-only feature with no release-build user path is not represented as working UI.

The shared settings components in `ui/settings/SettingsComponents.kt`, `ui/settings/SettingsRowDefaults.kt` and `ui/common/WhiteNoiseDialogs.kt` have their first release-build user path on the Appearance screen and are covered by `SET-001`–`SET-008`. `ui/common/WhiteNoiseTextField.kt` and the shared `SettingsSwitch` row have no release-build user path yet; they are listed in `docs/manual-release-testing-surfaces.json` as explicit coverage exceptions and are pinned by `WhiteNoiseTextFieldBehaviorTest`, `WhiteNoiseTextFieldScreenshotTest`, `SettingsComponentsSemanticsTest` and `SettingsComponentsScreenshotTest`. When a screen adopts them, replace those exceptions with permanent owning-prefix IDs in the same pull request.

### Maintenance contract

- Any pull request that adds, removes, renames, or changes user-visible behavior or state must update the affected point(s) in this guide in the same pull request. This includes permissions, intents, navigation, settings, error/retry copy, build-flavor differences, background work, privacy behavior, and accessibility behavior.
- Keep existing IDs forever. Edit a point in place when its feature changes; append a new ID within the owning prefix for a new independently reportable behavior; mark removed behavior as retired in the pull request rather than reassigning its ID.
- Every checklist point must remain an ordered Markdown checklist item with exactly one stable `<AREA>-<NNN>` ID, an action instruction a novice can execute, and one observable `**Expected:**` result after the `→` separator.
- Before opening or updating a pull request, run `python3 scripts/check_manual_test_guide.py`, `python3 -m unittest scripts/test_check_manual_test_guide.py`, and the repository's required Hermes fast gate. Review the scope map whenever navigation, resources, manifest components/permissions, tests, or release documentation changes.
